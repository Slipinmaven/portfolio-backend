# Backend instructions

These instructions extend the repository-root `AGENTS.md`. Confirm design
status in `docs/` before making product or schema decisions; those documents
distinguish confirmed behavior from proposals and unresolved questions.

## Architecture and ownership

- The backend uses FastAPI, Pydantic, SQLAlchemy's async API with PostgreSQL,
  and Alembic. Keep the existing dependency direction:
  - `presentation/`: FastAPI endpoints, request/response schemas, dependencies,
    middleware, and HTTP mapping.
  - `application/`: use-case services, DTOs, and application errors.
  - `infrastructure/database/`: SQLAlchemy models, repositories, sessions, and
    units of work.
  - `infrastructure/security/`: password and token primitives and related
    security helpers.
  - `core/`: cross-cutting configuration and logging.
- Endpoints should translate HTTP input to application DTOs and application
  results to response schemas. Keep business rules out of routes and SQL
  queries out of services.
- Services coordinate business rules and transaction boundaries through the
  appropriate unit of work. Repositories own persistence queries and must not
  commit transactions. Follow the established flush/commit/rollback pattern;
  keep related writes, such as content changes and audit records, atomic.
- Use Pydantic request/response schemas at the HTTP boundary and typed DTOs
  between presentation and application layers. Preserve explicit partial-update
  semantics and reject fields the API does not allow.
- Reuse existing application errors and the exception-handling middleware for
  expected failures. Do not mask unexpected failures with success-shaped
  responses or broad silent fallbacks.
- Use FastAPI dependencies for session, unit-of-work, service, and user
  injection. Do not create database engines or sessions outside their
  established lifecycle.

## Data, migrations, and API behavior

- Enforce important invariants at both the application boundary and the
  database where appropriate. Consider foreign keys, uniqueness, nullability,
  check constraints, indexes, query count, pagination, and concurrent writes.
- Keep ORM models in `infrastructure/database/models/` and export each model
  from that package so Alembic can discover its metadata.
- Create migrations only for approved schema changes. Review every
  autogenerated migration for data safety, constraint behavior, ordering, and
  downgrade implications before applying it. Do not infer approval from a
  proposed design document.
- Preserve public/admin visibility boundaries. Check the existing route
  policy and product decision for each endpoint; do not assume all editorial
  features have the same role requirements.
- Use the existing pagination bounds and response envelope conventions where
  applicable. Avoid N+1 queries and load relationships explicitly when
  responses need them.

## Authentication, secrets, and observability

- Enforce HTTP authentication and role permissions at the FastAPI boundary
  with `get_current_user` and the existing role dependencies; never rely on
  frontend checks. Add application-level authorization only when it is a
  business rule that must also hold for non-HTTP callers, and avoid duplicating
  route permission checks in services.
- Use the established password/token helpers. Never store or log plaintext
  passwords, access or refresh tokens, cookies, signing keys, or other
  credentials. Treat user-agent and client IP data as untrusted input.
- Read settings through `app.core.config`; keep secrets in environment
  configuration and `SecretStr` fields. Treat a real `.env` as sensitive: do
  not copy, display, log, transmit, or commit secret values. Inspect it only
  when necessary for the task, and keep any checks targeted and redacted.
- Use the existing application, error, and security logging helpers. Log
  useful event context without leaking credentials or unnecessary personal
  data; preserve request IDs and established error handling.

## Tests and checks

- Backend tests use `unittest`, `unittest.mock`, `AsyncMock`, and
  `IsolatedAsyncioTestCase` for async behavior. Route tests use FastAPI's
  `TestClient` and dependency overrides. Follow those patterns unless the
  project deliberately adopts another runner.
- From `backend/`, with the backend development environment active (or using
  its Python interpreter), run focused tests with
  `python -m unittest discover -s tests -p "test_<area>.py"`; run the full
  suite with `python -m unittest discover -s tests`.
- Applying migrations and database-dependent checks require a reachable
  configured database. Alembic can also render SQL offline, for example with
  `python -m alembic -c alembic.ini upgrade head --sql`. Report unavailable
  validation explicitly.
- Update `backend/README.md` and the relevant design reference when API,
  security, setup, or schema behavior changes.
